## 1. Notifikasi Telegram admin

**Temuan awal yang mengubah arah pekerjaan:** kodenya sudah ada sejak Fase 7b dan
dipanggil di enam titik. Yang bolong konfigurasinya — `TELEGRAM_BOT_TOKEN` /
`TELEGRAM_CHAT_ID` dibaca dari environment variable, dan kalau kosong pengiriman
dilewati dengan `console.error` saja. Di deployment yang env-nya belum diisi,
seluruh notifikasi (order gagal, refund, saldo provider habis) hilang tanpa satu
pun tanda yang terlihat admin.

**Yang berubah:**

- Token & chat ID pindah ke `SiteSetting` terenkripsi (`lib/notify/telegram-config.ts`),
  pola sama dengan `email-config.ts`. Env lama tetap jadi fallback supaya deployment
  lama tidak mendadak bisu saat rilis ini naik.
- Sepuluh jenis event dengan centang masing-masing + satu saklar induk.
- Tombol **Kirim Tes** di `/admin/settings` — ini yang membuat "tokennya benar atau
  tidak" bisa dibuktikan, bukan ditebak.
- Event baru yang sebelumnya tidak ada sama sekali: order dibuat, pembayaran
  diterima, **order berhasil**, order manual masuk, deposit masuk, user baru daftar.

**Yang perlu diperhatikan saat menambah event baru:** `notifyTelegram()`
mengembalikan `"sent" | "disabled" | "failed"`, bukan boolean. Pemanggil yang
memakai hasil kirim sebagai gerbang penulisan state (lihat `check-provider-balance`
di `lib/jobs/runner.ts`) **wajib** memperlakukan `"disabled"` sebagai tuntas —
kalau tidak, mematikan sebuah kategori notifikasi akan membekukan state machine-nya
selamanya.

Event yang default menyala sengaja bukan "semua": `order_created` dan `order_paid`
terkirim untuk tiap transaksi, dan di toko yang ramai itu membanjiri chat sampai
alert yang penting ikut terabaikan.

## 2. Invoice, email, dan struk cetak

- **Identitas dokumen** (`lib/invoice/branding.ts`) — logo, nama brand, warna aksen,
  tagline, alamat, kontak, kalimat penutup. Dipakai bersama oleh email, halaman
  invoice, dan struk. Diubah sekali, berlaku di ketiganya.
- **Template email** (`lib/notify/email-templates.ts`) — lima template
  (pesanan diterima / berhasil / bermasalah, selamat datang, reset password) yang
  subjek & badannya bisa diedit admin, lengkap dengan pratinjau memakai data contoh.
  Kerangka luarnya (logo/header/kaki) **tidak** ikut diedit per template: lima
  salinan header berarti mengganti logo harus dikerjakan lima kali, dan yang terlupa
  satu akan diam-diam mengirim logo lama selamanya.
- **Struk cetak** di `/invoice/[token]/struk` — 58 mm, 80 mm, dan A4/PDF.

**Angka lebar struk bukan karangan.** Printer termal mencetak dengan font monospasi
berukuran tetap (Font A, 12×24 dot), jadi jumlah karakter per baris ditentukan lebar
cetak kertasnya: **58 mm → area cetak ~48 mm → 32 karakter**, **80 mm → ~72 mm → 48
karakter**. Teksnya dirakit di server untuk kedua ukuran sekaligus lalu dikirim jadi
ke klien, supaya perataan kolomnya identik antara layar, kertas, dan aplikasi
pencetak.

**Soal printer Bluetooth:** browser tidak bisa mencetak langsung ke printer termal.
Web Bluetooth tidak tersedia di iOS sama sekali dan menuntut implementasi ESC/POS
penuh di sisi kita. Jalur yang benar adalah menyerahkannya ke aplikasi pencetak
Android yang sudah menangani pemasangan perangkat & encoding — tombol "Printer
Bluetooth" membuka skema URL `rawbt:`. Tombol "Salin Teks" ada sebagai jalan keluar
kalau aplikasinya tidak terpasang.

### Keamanan template

Nilai data (`{{order_number}}`, `{{buyer_email}}`, …) **selalu** di-escape saat
dirender; sebagian di antaranya diketik pembeli sendiri. Yang dimasukkan apa adanya
hanya **blok** (`{{order_table}}`, `{{sn_box}}`, …) yang HTML-nya dibangun kode kita.
Pemisahan itu adalah inti keamanan `lib/notify/template.ts` — jangan dikaburkan.

## 3. Kustomisasi storefront

**Ruang lingkupnya sengaja terbatas, dan itu keputusan desain — bukan kekurangan.**

Yang bisa diubah admin di `/admin/appearance`: warna & radius tema, CSS kustom, dan
potongan HTML pada **12 slot** yang sudah ditentukan (beranda, daftar produk, detail
produk, form checkout, halaman transaksi, struk, deposit, login, daftar).

Yang **tidak** bisa: mengganti markup halaman login, checkout, invoice, atau deposit.
Halaman-halaman itu komponen React ber-state yang menjalankan Snap.js, polling status
tiap tiga detik, dan Server Action ber-CSRF. Markup buatan admin tidak akan tersambung
ke satu pun di antaranya — tombol bayarnya akan terlihat benar tapi tidak melakukan
apa-apa, dan kerusakan itu baru ketahuan dari pembeli yang uangnya sudah keluar.

### Penyaring HTML

`lib/storefront/sanitize-html.ts` memakai **daftar-izin**, bukan daftar-larang.
Daftar-larang selalu kalah — selalu ada bentuk yang belum terpikirkan
(`<svg><script>`, `java\tscript:`, `data:text/html;base64,…`).

HTML slot disaring **dua kali**: saat disimpan dan saat dibaca. Penyaringan ganda
disengaja — baris `SiteSetting` bisa saja pernah ditulis lewat jalur lain (skrip,
akses DB langsung, versi kode lama), dan halaman publik tidak boleh bergantung pada
asumsi bahwa semua isi DB pasti bersih. Alasan semua ini ada: HTML tersebut tampil
satu halaman dengan nomor Virtual Account. Kalau satu akun admin jebol, penyaring ini
mengubah "bencana" jadi "kerugian terbatas".

**CSS kustom hanya dipasang di layout storefront publik**, tidak global. Kalau global,
satu aturan salah ketik (`div{display:none}`) ikut mematikan panel admin — dan panel
admin satu-satunya tempat memperbaikinya lagi.

## 4. Analytics

Tabel `PageView` (mentah, retensi 30 hari) + `AnalyticsDaily` (rollup permanen),
diringkas job cron `rollup-analytics` tiap 6 jam sebelum baris mentahnya dibuang.

**Tidak menyimpan alamat IP.** `visitorHash` = SHA-256 dari (IP + user agent + garam
harian rahasia). Cukup untuk menghitung pengunjung unik dalam satu hari, tidak bisa
dibalik jadi identitas, dan **berganti tiap hari** sehingga tidak bisa dipakai
merangkai jejak seseorang antar-hari.

Konsekuensi yang wajib disebut di UI dan sudah ada di halamannya: angka "pengunjung"
untuk rentang berhari-hari **bukan** jumlah orang berbeda — satu orang yang datang
tiga hari terhitung tiga kali.

**Pencatatan lewat endpoint beacon (`/api/track`), bukan middleware.** Middleware
berjalan untuk setiap aset, prefetch, dan perayap; menulis satu baris DB untuk
masing-masing akan menghabiskan biaya database jauh sebelum menghasilkan data yang
berguna.

**Tampilan langsung memakai polling 10 detik, bukan SSE/WebSocket.** Di runtime
serverless, koneksi yang dibuka terus dibayar per detik — satu tab admin yang lupa
ditutup semalaman jadi tagihan compute semalam penuh. Polling juga otomatis berhenti
saat tab tidak terlihat.

### Pagination & refresh

- `lib/admin/pagination.ts` — batas dipusatkan. Sebelumnya tiap halaman memilih
  sendiri (`take: 50`, `take: 100`), dan **halaman produk tidak punya batas sama
  sekali** — menarik seluruh tabel produk tiap kali dibuka, tumbuh diam-diam sampai
  suatu hari melewati batas memori dan mati total.
- Dropdown 20/50/100/200 dengan **batas atas keras 200** — nilainya datang dari query
  string yang bisa diketik siapa saja; tanpa penjepit, `?per=100000` adalah satu
  permintaan yang bisa menjatuhkan panel.
- Filter tanggal di Orders, Mutasi Saldo, Log API Provider, Log Callback.
- Tombol **Refresh** (`router.refresh()`) — memuat ulang data tanpa kehilangan posisi
  scroll, isian form, dan tab yang sedang terbuka.

## 5. Cek ID / server game

Digiflazz **tidak** menyediakan validasi akun game (API mereka hanya punya inquiry
pascabayar/PLN), jadi datanya wajib dari layanan pihak ketiga. Karena penyedia semacam
itu sering berganti dan mati, yang dibangun adalah **adapter generik**: URL, metode,
header, dan letak nickname di dalam respons JSON semuanya diisi admin di
`/admin/id-check`. Ganti penyedia = ganti isian, bukan ganti kode.

Kolom `Product.nicknameCheckKey` sudah ada sejak migrasi awal tapi **tidak pernah
dibaca kode mana pun**; sekarang dipakai sebagai kode game untuk placeholder `{game}`.

Dua kontrol terpisah: saklar induk global + centang per produk. Admin bisa mengisi &
mengetes kode gamenya lebih dulu, baru menyalakannya untuk pembeli — dan bisa
mematikannya saat API penyedia bermasalah tanpa kehilangan konfigurasi yang benar.

**Penjagaan SSRF:** URL diisi admin dan di-fetch server kita. Tanpa penyaring host,
panel admin berubah jadi alat memindai jaringan internal — termasuk endpoint metadata
penyedia cloud yang menyimpan kredensial. Hanya `https://` ke host non-privat yang
diizinkan. Jalur publiknya juga dibatasi 15 permintaan/menit per IP supaya kuota API
penyedia tidak habis dipakai orang yang menjadikan toko kita proksi cek ID gratis.

## 6. Produk manual (App Premium)

`Product.fulfillmentMode` = `AUTO` | `MANUAL`, disnapshot ke `Order.fulfillmentMode`
saat checkout. Snapshot, bukan bacaan ulang: kalau admin mengubah produk dari MANUAL ke
AUTO, order lama yang belum tuntas tidak boleh mendadak dicoba dikirim ke provider yang
tidak punya SKU-nya.

**Alur:** pembeli bayar normal (Midtrans/saldo) → order jadi `PROCESSING` tanpa
diteruskan ke provider → notifikasi Telegram `order_manual` ke admin → halaman invoice
menampilkan tombol konfirmasi WhatsApp/Telegram berisi pesan bertemplate → admin kirim
produknya lalu **Tandai Selesai Manual** + isi SN/data akun.

**Sengaja BUKAN nilai baru pada enum `OrderStatus`.** Order manual melewati rangkaian
status yang sama persis (`PAID → PROCESSING → COMPLETED`); yang berbeda hanya siapa
yang menuntaskannya. Menambah status baru berarti menyentuh setiap switch/label/filter
status yang sudah ada tanpa memberi informasi tambahan.

**Dua bug saudara yang ditemukan & diperbaiki bersamaan** — keduanya menggantungkan
"produk ini bisa dibeli atau tidak" pada keberadaan SKU provider, yang untuk produk
manual memang tidak akan pernah ada:

| Lokasi | Gejalanya kalau tidak diperbaiki |
|---|---|
| `actions/checkout.ts` — gerbang `selectFulfillmentSku` | Setiap checkout produk manual ditolak "Item ini sedang tidak tersedia" |
| `lib/catalog/public.ts` — `isItemPurchasable` | Semua nominal produk manual tampil abu-abu di katalog |

Kalau nanti ada titik ketiga yang menilai hal serupa, `fulfillmentMode` wajib ikut
dipertimbangkan di sana juga.

## 8. Yang harus dijalankan sebelum/sesudah deploy

### Migrasi (WAJIB, sekali)

```
cd web
npx prisma migrate deploy
```

Satu file: `20260809140000_add_analytics_manual_fulfillment_id_check`. Isinya
**seluruhnya aditif dan berdefault** — tidak ada kolom yang dihapus, tidak ada yang
berubah tipe, tidak ada backfill. Deployment kode lama tetap berjalan normal setelah
migrasi ini naik, jadi urutan deploy-vs-migrasi tidak menciptakan jendela rusak.

Yang ditambahkan: `Product.fulfillmentMode`, `Product.idCheckEnabled`,
`Order.fulfillmentMode`, tabel `PageView`, tabel `AnalyticsDaily`.

### Environment variable

**Tidak ada yang baru.** `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` masih dibaca sebagai
fallback, tapi sekarang lebih baik diisi lewat `/admin/settings` — di sana ada tombol
Kirim Tes yang membuktikan konfigurasinya benar, sesuatu yang tidak bisa dilakukan env
var.

`CREDENTIALS_ENCRYPTION_KEY` yang sudah ada sekarang dipakai juga untuk garam harian
`visitorHash`. **Menggantinya akan mereset perhitungan pengunjung unik hari itu** (dan,
seperti sebelumnya, membuat seluruh kredensial tersimpan tidak bisa didekripsi).

### Langkah setelah deploy

1. `/admin/settings` → isi bot token & chat ID → **Kirim Tes** sampai pesannya sampai.
2. `/admin/invoice` → isi identitas dokumen (logo, nama, kontak) — ini yang muncul di
   semua email & struk.
3. `/admin/id-check` → isi URL penyedia, **Jalankan Tes**, baru nyalakan.
4. Job `rollup-analytics` terdaftar otomatis lewat `ensureRecurringJobs()` pada tick
   cron berikutnya — tidak perlu tindakan manual, tapi pastikan cron-nya memang jalan
   (`/admin/jobs`).
